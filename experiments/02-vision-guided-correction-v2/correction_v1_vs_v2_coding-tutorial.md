## 1. 배경 — 왜 v2를 만들었나

### v1(기존 프롬프트)의 문제

이전 실험(`experiments/vision-guided-correction/exp_compare_correction_on_20260412_063721.json`)에서 v1 correction을 켰을 때, 전사 세그먼트에 화면의 코드 블록·슬라이드 텍스트가 통째로 삽입되어 **"뒤죽박죽 전사"**가 생성됨. 예: 원문 12자 발화에 대해 LLM이 200자 넘는 코드 설명을 생성해서 반환.

### v1 프롬프트가 폭주한 원인

- "화면 기준으로 교정한다"라고만 지시 → LLM이 "화면 내용을 본문에 병합해 완성하라"로 오독
- 프레임 설명(긴 서술) + 세그먼트 발화(짧은 발화)의 **컨텍스트 비대칭** → 긴 쪽이 본문처럼, 짧은 쪽이 보조처럼 다뤄짐
- 출력 형식·길이 제약 없음

### v2의 설계 방향

보수적 교정으로 방향 전환. 주요 변경점:

1. **역할을 부정형으로 좁힘** — "받아쓰기 오류 수정자. 작가/요약자/재구성자가 아니다."
2. **frame_description을 "참조용 어휘집"으로 재정의** — 화면 내용을 본문에 옮겨 적지 않도록 명시 금지
3. **화이트리스트** — 프로그래밍 식별자(함수명·변수명·예약어)의 한글 음차 → 원어 영문 치환만 허용
4. **원문 구조 유지 강제** — "문장 수, 어절 수, 어순, 어미 유지. 출력 길이 ±10%"
5. **프레임 뒤집기** — "교정이 기본"이 아닌 **"유지가 기본, 교정이 예외"**
6. **JSON 출력 + changes 명시** — LLM이 변경 사항을 배열로 열거하게 해서 silent injection 억제

### 2차 방어선 — 코드 레벨 "리미터"

[correction_utils.py:`_parse_correction_response()`](../../app/correction_utils.py)에 **원문의 1.3배 초과 시 원문 유지** 로직을 추가. 프롬프트가 뚫려도 retrieval 오염을 막는 하드 가드. **v1, v2 양쪽에 동일하게 적용**되는 공통 안전망.

## 3. 진짜 차이 — 리미터 발동 횟수

두 실험의 본질적 차이는 aggregate 메트릭이 아니라 **코드 레벨 리미터가 얼마나 개입했는가**에 있다.

| 실험 | 매칭 세그먼트 | 리미터 발동 | 발동률 | 최악 사례                                    |
| ---- | ------------- | ----------- | ------ | -------------------------------------------- |
| v1   | 12            | **6건**     | 50%    | 12자 → 293자 (24.4배), 28자 → 463자 (16.5배) |
| v2   | 12            | **0건**     | 0%     | —                                            |

### v1 폭주 로그 (v1_fresh 실행 중 출력)

```
교정 결과가 원문의 1.3배 초과 (원문 유지): 40 → 378자
교정 결과가 원문의 1.3배 초과 (원문 유지): 30 → 41자
교정 결과가 원문의 1.3배 초과 (원문 유지): 21 → 106자
교정 결과가 원문의 1.3배 초과 (원문 유지): 35 → 68자
교정 결과가 원문의 1.3배 초과 (원문 유지): 28 → 463자
교정 결과가 원문의 1.3배 초과 (원문 유지): 12 → 293자
```

### 두 가드의 역할 분리

| 층                       | 역할                                                          | v1                                               | v2                                        |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------------- |
| **프롬프트 가드** (soft) | LLM이 폭주하지 **않도록 사전 유도**                           | 약함 — LLM을 실질적으로 제약 못함                | 강함 — 화이트리스트·길이 제약·부정형 규정 |
| **코드 가드** (hard)     | LLM 응답을 **돌려받은 후 길이 체크** (1.3배 초과 → 원문 복구) | **6번 개입 (50% 호출에서 프롬프트 실패를 수습)** | 0번 (프롬프트가 이미 차단)                |

### 이게 의미하는 것

v1 결과물이 메트릭상 "괜찮아 보이는" 이유는 **v1 프롬프트가 제대로 작동했기 때문이 아니다**. 50% 호출에서 LLM이 여전히 10~24배로 폭주했고, 코드 가드가 이 6개를 버리고 원문으로 복구했기 때문에 DB에는 깔끔한 텍스트가 들어갔을 뿐.

**비유**:

- v1 = 속도 제한 표지만 있는 도로 + 리미터 장착 차량. 운전자는 자주 과속하지만 리미터가 강제 감속.
- v2 = 운전자 교육도 잘 되어 있고 리미터도 있는 차량. 리미터가 개입할 일이 없음.

**리미터를 제거하면**:

- v1: 6개 폭주 세그먼트가 그대로 DB에 삽입 → 이전 "뒤죽박죽" 재현
- v2: 변화 없음. 프롬프트 레벨에서 이미 차단.

## 4. 질문별 비교

### T1 — 비전질문

**쿼리:** 영상에서 사용된 파이썬 내장 함수를 모두 나열해줘

| 항목                        | v1                                           | v2                                           |
| --------------------------- | -------------------------------------------- | -------------------------------------------- |
| **답변**                    | `input()`, `split()` — `int()`, `len()` 누락 | `input()`, `split()` — `int()`, `len()` 누락 |
| **AR / GR / RP**            | 0.70 / 1.00 / 0.00                           | 0.70 / 0.70 / 0.00                           |
| **검색 청크 (chunk_index)** | 3, 2, 4                                      | 3, 2, 4                                      |

**비고:** 거의 동일한 청크를 retrieval. 두 경우 모두 `int`, `len`이 포함된 후반부 청크를 못 찾아 답변 누락. v2가 GR 0.30 하락한 건 분산 범위로 보임. correction 효과가 드러나는 질문 아님.

### T2 — 비전질문

**쿼리:** total 변수의 초기값은 무엇인가?

| 항목             | v1                                    | v2                                                |
| ---------------- | ------------------------------------- | ------------------------------------------------- |
| **답변**         | total 변수의 초기값은 0 (근거 [105s]) | total 변수의 초기값은 0 (근거 [90s] [75s] [105s]) |

**쿼리:** 점수를 입력받을 때 사용한 구분자는 무엇인가?

| ---------------- | ------------------------- | ------------------------- |

### T5 — 비전질문

**쿼리:** 평균을 계산하는 코드는 어떻게 작성되어 있는가?

| 항목             | v1                                                                  | v2                                          |
| ---------------- | ------------------------------------------------------------------- | ------------------------------------------- |
| **답변**         | 전체 코드 제시 (`input()`, `split()`, `for`, `int()`, `len()` 포함) | `total / len(score_list)` 등 핵심 코드 제시 |

**비고:** **v2가 GR에서 0.40 → 1.00으로 크게 개선**. v1은 답변이 장황하고 일부 근거가 명확하지 않았으나(GR 0.40), v2는 더 간결하고 정확한 근거를 제시. RP는 v1이 우세지만 GR 차이가 훨씬 커서 질적 답변 품질은 v2가 우세.

## 5. full_transcript 수준 관찰

### v1 full_transcript 샘플 (2120자)

v1에서 통과한 교정(리미터 발동 6건 제외한 나머지)의 예:

- 원문 "그래서 한 번에 받되 쉼표로 구분해서 받도록 합시다" → **원문 그대로** (또는 마침표만 추가)
- 원문 "그 리스트의 길이를 가져오는 걸 랜이라고 합니다" → **"...걸 len이라고 합니다"** (올바른 치환)
- 원문 "랭프의 줄임말이죠" → **"랜프의 줄임말이죠"** (의미 없는 변경)

리미터로 돌려보낸 6건은 모두 원문 그대로 보존되어 DB에 저장됨. 결과적으로 full_transcript는 대부분 원문 + 소수의 소폭 수정 형태.

### v2 full_transcript 샘플 (2137자)

v2 교정의 예:

- 원문 "유저 인풋, 이 점수들에 대한" → **"user input, 이 점수들에 대한"** (화이트리스트 치환 성공)
- 원문 "점스플릿 한 다음에 스플릿이 모여서" → **"점수를 split 한 다음에 split이 모여서"** (치환은 맞으나 "점수를"이라는 불필요한 삽입)
- 원문 "걸 랜이라고 합니다" → **"걸 len이라고 합니다"** (올바른 치환)

### v2의 실수 유형 1 — "쉼표" → "input" (과잉 치환)

```
원문: 그래서 한 번에 받되 쉼표로 구분해서 받도록 합시다
v2:   그래서 한 번에 받되 input으로 구분해서 받도록 합시다
```

"쉼표"는 프로그래밍 식별자가 아니므로 화이트리스트 대상이 아니다. v2 프롬프트에 "허용되는 것만 바꿔라, 그 외는 원문 유지"라고 명시했음에도 LLM이 **화면의 `input()` 코드를 보고 어긋난 치환을 시도**. 화이트리스트 **밖**을 건드린 사례.

이 실수는 길이 1.3배 이내라 리미터에는 걸리지 않음.

### v2의 실수 유형 2 — "프린트" → (변경 없음) (누락 치환)

```
원문 [120~140s]: ... 마지막으로 뭐 프린트를 하면 되겠죠 그래서 전체 코드를 보면 ...
v2  [120~140s]: ... 마지막으로 뭐 프린트를 하면 되겠죠 그래서 전체 코드를 보면 ...
```

"프린트"는 Python 내장 함수 `print()`의 한글 음차. v2 화이트리스트의 **명시적 허용 대상**이다("함수명·변수명·예약어의 한글 음차 → 원어 영문"). 그런데 LLM이 이 지점에서 치환을 **하지 않고 지나감**. 화이트리스트 **안**인데도 놓친 사례.

같은 구간의 프레임 분석에는 코드 맥락이 충분히 있었음에도 불구하고 LLM이 "이건 치환해야 한다"고 판단하지 않음. 바로 직전 세그먼트들에서는 "랜" → "len", "유저 인풋" → "user input" 같은 치환은 잘 수행했기 때문에, **동일 프롬프트·동일 모델·동일 세션 내에서도 LLM의 치환 여부가 일관되지 않다**는 것이 핵심.

### 두 실수 유형이 보여주는 것 — LLM 기반 교정의 구조적 한계

- **과잉 치환 (false positive)** — "쉼표" → "input". 프롬프트가 화이트리스트 **밖**을 못 지킴
- **누락 치환 (false negative)** — "프린트" 그대로. 프롬프트가 화이트리스트 **안**도 못 지킴

이 두 유형이 **동시에** 나타난다는 점이 결정적이다. 어느 한쪽만 있다면 프롬프트를 더 강하게(또는 약하게) 조정해서 해결 시도해볼 수 있지만, 둘이 공존한다는 건 "LLM의 판단을 프롬프트만으로 충분히 좁힐 수 없다"는 신호에 가깝다.

보수적으로 만들면 누락이 늘고, 적극적으로 만들면 과잉이 는다. 이 트레이드오프를 프롬프트 엔지니어링만으로 동시에 해결하려는 시도는 비용 대비 효율이 낮을 가능성이 있음. **결정론적인(deterministic) 경로를 병행해야** 두 유형이 동시에 줄어든다.

## 6. 종합 분석

### correction v1 → v2의 진정한 성과

1. **폭주 제거**: 50% → 0%. LLM이 문단 재구성을 시도하는 빈도가 사라짐.
2. **리미터 의존도 제거**: v1은 리미터(코드 가드) 없이는 "뒤죽박죽 전사"가 그대로 DB에 들어감. v2는 리미터가 없어도 안전.
3. **프롬프트 레벨 방어 구축**: 프롬프트가 LLM 행동을 효과적으로 제약하는 구조가 됨. 1차 방어선이 실질적으로 작동.
4. **WER 개선**: 0.0515 → 0.0258. 폭주가 사라지면서 전사 정확도가 절반 수준으로 낮아짐.

### v2의 한계

1. **Aggregate 메트릭 호각**: AR 동일, RP는 오히려 v1 우세(0.53 vs 0.40). LLM-as-judge의 분산 안쪽으로 보이지만, 보수적 교정이 "일부 유용한 치환 기회"도 함께 놓쳤을 가능성 있음.
2. **잘못된 치환 잔존**: "쉼표" → "input"처럼 **화이트리스트 밖 단어를 건드리는 silent mistake**가 남아 있음. 프롬프트의 의미적 경계를 LLM이 항상 존중하지는 않음.
3. **n=5 한계**: 질문 5개로는 v2의 우위를 통계적으로 단정하기 어려움. 다른 데이터셋·더 많은 질문으로 재검증 필요.

### 왜 aggregate 메트릭이 극적으로 좋아지지 않았나

폭주 세그먼트가 이미 리미터에 의해 원문으로 복구되어 있기 때문에, **v1도 최종 DB 콘텐츠는 상당히 깨끗한 상태**였다. 따라서 retrieval 품질의 대부분이 비슷하게 나옴. v2의 이득은 주로:

- "만약 리미터가 없다면" 나올 재앙을 원천 차단 (잠재 위험 제거)
- 디버깅·신뢰성 측면의 향상 (로그에 warning이 찍히지 않음 → 이상 지점 수색 비용 감소)
- 프롬프트 견고성 — 다른 데이터셋·다른 비전 프롬프트 환경에서도 안정적으로 작동할 가능성

즉 **v2의 가치는 "이미 안정된 상태를 더 안정화"하는 데 있지, "깨진 것을 수치적으로 극적 개선"하는 데 있지 않다**.

## 7. 남은 과제

### 7.1 가장 중요한 전환점 — 토큰 치환(단어 사전) 방식 병행

이번 실험의 가장 큰 인사이트는 **v2에서 "프린트"가 치환되지 않았다**는 사실이다. 이는 "프롬프트를 아무리 잘 써도 LLM은 치환을 일관되게 수행하지 못한다"를 증명한 사례. 처음에는 토큰 치환이 "한정된 컨텍스트에만 대응 가능하다"는 이유로 LLM 방식을 선택했지만, **실제로는 LLM도 한정된 상황에서만 일관되게 작동**함을 확인.

따라서 다음 단계 방향성:

- **1차(결정론적): 단어 치환(dictionary) 경로** — Python 예약어·내장 함수·일반적인 음차 패턴("프린트" → `print`, "랜" → `len`, "폴루프" → `for 루프`, "인풋" → `input`, "스플릿" → `split` 등)을 고정 dictionary로 구축. 후처리 단계에서 regex 기반 치환. **모든 등장 위치에서 100% 일관**.
- **2차(맥락적): LLM 교정** — dictionary에 없는 상황별 고유 식별자(예: 이 강의에서만 쓰는 변수명 `user_input_scores`, `score_list`)만 LLM이 맥락 기반으로 처리. 화이트리스트를 "dictionary로 못 잡는 것만"으로 더 좁힘.
- **실험 제안**: v3 = dictionary 단계 + v2 프롬프트의 축소판. 기대 효과 — 누락(프린트)·과잉(쉼표→input) 둘 다 감소.

이게 가능한 이유는 두 방식의 실패 양상이 **상호보완적**이기 때문이다:

- Dictionary: 사전에 없는 것(강의별 고유 변수명)을 놓침 — but 사전 내 항목은 100% 처리
- LLM: 사전 내/밖 상관없이 일관되지 않음 — but 맥락을 볼 수 있음

### 7.2 기타 후속 실험

- **다른 데이터셋 검증** — coding-tutorial 하나로는 일반화 판단 불가. interview 등 다른 dataset에서 v1·v2 비교 재실행 필요.
- **화이트리스트 정교화** — v2 프롬프트에 few-shot 예시 확장, 특히 "프린트"처럼 자주 나오는 음차 패턴을 명시적으로 나열하는 방법 시도 가능. 다만 §7.1의 dictionary 경로가 더 근본적 해결책일 가능성.
- **"유용한 치환을 놓치는 문제" 재검토** — RP가 v1 우세인 점이 분산인지 체계적 손실인지, 질문 세트를 늘려서 확인.
- **스냅샷 정합성 개선** — 실험 JSON에 `fixture.created_at`, `fixture.config` 메타도 기록하도록 개선. 이번 세션에서 "snapshot ≠ fixture 실제 콘텐츠" 양다리로 인한 혼란이 있었음.
